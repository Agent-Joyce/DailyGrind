# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository

The project is the GitHub repo **`Agent-Joyce/DailyGrind`**. Work happens in a clone of it, on `main`. Throwaway files (hooked test copies, scripts, simulation and UI-check output, screenshots) go in a folder outside the repo, such as the session scratchpad, and are never committed.

## What this is

Daily Grind is a browser life-sim game that lives in **one file: `index.html`** (~6,400 lines: CSS, markup, then a single `<script>` wrapped in one IIFE). There is no build step, package manager, linter or unit-test suite. `CHANGELOG.md` is the running record of every gameplay change (no README). `docs/` holds the `CONFIG` guide (`Daily Grind Config Guide.docx`, keep it in step when `CONFIG` changes), the simulation reports (`QA_Sim_*`) and an older snapshot QA report (`QA_Report.html`). `tools/qa/` holds the QA scripts: `sim.js` with its launcher `run-sims.js` (simulation runs) and `uicheck.js` with its launcher `run-uicheck.js` (the UI check). The `.ps1` files there are older Windows launchers and are not used. **`CODE_MAP.md` says where everything is in `index.html` (twelve numbered sections) and how to add an action, building, event, CONFIG value or save change; keep it current when you move or add a section.**

## Running and checking changes

- Test in headless Chromium with Playwright (installed in the cloud environment), against a throwaway copy of `index.html` with a test hook injected just before the line `  if(!load())fresh();`. The hook assigns `window.__G` to expose the closure's internals (`S`, `CONFIG`, `fresh`, `enter`, `render`, `worth`, ...); everything is private to the IIFE, so nothing can be driven from outside without it. Keep that marker line unique and intact. Do not commit the copy.
- Game state autosaves to `localStorage` (`dailyGrind.save.v1`), so clear it when testing a fresh start.
- Seed `Math.random` in the page before running anything that must be repeatable. Events, illness, shocks and market noise all use it.
- Drive the UI with real clicks on `#shop [data-act]` buttons, `#hudEnd` (end day or "Sleep outside") and `#event [data-act]` (event choices) rather than calling functions, so button wiring is exercised too.
- **Ask before running simulations.** Simulation runs (`tools/qa/sim.js`, 20 careful + 10 random games per build) are not required for every gameplay change. After a gameplay change, ask the user whether they want them run, and only run them if they say yes. Targeted checks of the change itself (driving the game through the test hook) are still expected. To run them: `node tools/qa/run-sims.js <folder outside the repo>` (defaults: 20 careful games from seed 1, 10 random from seed 101; add `[survive] [random] [surviveSeed] [randomSeed] [page]` to change them or to run another copy of `index.html`, such as the base build when comparing two builds). It builds the hooked copy `sim.js` needs and writes `results.json`. The careful player works, studies, eats, banks, buys clothes and looks after its morale (`moraleStep()`: family calls, Park walks, the Community Centre); add `--no-comm` to keep it out of the Community Centre, and `--rivals=easy|medium|expert|mixed` (`--rival-count=1..3`) to play 30-day games with AI rivals (each result then lists the rivals' outcomes). Each result records the morale activities used (`morale`).
- **Every simulation run report must be saved to `docs/`** (not only in scratch files), as soon as the run finishes. Name it `QA_Sim_<date>_<change>`. Save a readable `.md` report and the raw results as `.json` (`window.__QA_RESULTS`). Both must record the version tested: the base commit, plus the CHANGELOG section of any uncommitted change. They must also record the run settings (players, seeds) and, when two builds are compared, which result belongs to which build. Link the report from that change's CHANGELOG entry.
- **UI check: run it whenever the user asks** (for example "run the UI check", "check the buttons", "check the UI on desktop and phone"), with `node tools/qa/run-uicheck.js <folder outside the repo>`. `tools/qa/uicheck.js` sets up a game with something to press everywhere, presses every enabled button in every building (restoring the game between presses), checks the status page, the action preview, a certificate and ending the day, and runs extra situations (sick with the flu and medical bills, sick with dengue, sick at home, rent arrears, a loan to repay, a pawned item to redeem, an industry-specific storyline, out of clothes, bank offers, the phone home screen, the Bank and Jobs apps, a friend's job tip, a rival's job race, meeting and calling rivals, the Messages app with rival loans and bets, a flatmate (home, out, none yet), a study group, and a night with a rival card; `SITUATIONS` in `uicheck.js`, which also reports MISSING when a situation's buttons do not appear). It reports script errors, dead buttons, missing toasts, log text / toast icons / row chips that disagree with the real change in time and vitals, layout problems (sideways scrolling, things off screen or out of their card, clipped button labels, buttons over text) and "NaN"/"undefined" on screen, at desktop (1280×800) and phone (390×844) width, and saves a screenshot of every screen. The launcher then runs reload checks the page cannot do itself: each difficulty, a starting trait, save and reload mid-game, and a damaged save. Report every issue to the user, fix the real ones and say which are not bugs. When a new button or panel needs setup to be pressable (a job, an item, a state), add it to `setup()` or `SITUATIONS` in `uicheck.js`. A check of the check: `node tools/qa/run-uicheck.js <folder> <copy of index.html>` runs it on a deliberately broken copy.

## Committing

- Changes that touch neither the UI nor gameplay (CLAUDE.md, docs, QA tools): commit and push to `main` when done.
- Changes that touch the UI or gameplay: after the targeted checks, ask the user whether to run the UI check and/or the simulations first. Run what they ask for, report the results, then commit and push to `main` (or hold the commit if they say so).
- Commit straight to `main` and end commit messages with the session's attribution lines.

## Architecture

**One mutable state object `S`** (`blank()` is the full schema) plus a `CONFIG` object at the top of the script. `CONFIG` is the single source of tunable numbers, one top-level key per topic (listed in the banner above it), each with its own comment. Gameplay values (pay shifts, food energy, loan rates, bankrupt rule, sleep, health, market sensitivity, macro strength) belong in `CONFIG`, not inline.

**Rules text is generated from CONFIG.** The Rules overlay in the HTML has `<span id="cfg...">` placeholders filled in from `CONFIG` (the setters in `timeText`, section 10, plus `paintBurnRules`). When you change a rule or its numbers, update the matching `cfg*` text so the screen still describes the logic. Text and logic drifting apart was the most common bug found in QA.

**Day cycle.** Player actions spend `S.ap` (minutes, `MAX_AP` = 1440 per day). Ending the day goes `endWeek(rested)` (decides where you slept, sets `restBonus`/`restHap`/`slept`, then `pickNight()` picks tonight's cards, stored in `S.pending`) then, when the player dismisses it, `rollover()` (the overnight pipeline). `rollover` order matters: clothes wear, energy and happiness (sleep, the nightly change, gadgets, coffee, hunger), food spoilage, pawn tickets, knowledge, workplace closures (`shutTick`), `trendTick` (macro effects), `indTick` (industry-specific storyline layoffs and suspensions), `rivalTick` (AI rivals' day, rival games only), gadget breakdowns, `tickInv` (investments), `healthTick`, `burnTick`, school expulsion, `loanTick`, `stressTick` (game-over checks: bankrupt, hospital, exhaustion, morale), savings interest, rent and arrears, then sampleNight(wasFed) records the player and rivals before the morning summary and notes. Several steps return early when they end the game; finish() samples the effects reached on that final night before drawing the score. A lastDay field in each life record prevents duplicate sampling. Existing ending checks still run before rent; the fix does not reorder gameplay.

**Events and the effect-token mini-language.** Event outcomes are strings of space-separated tokens parsed by `applyFx0` using `tokRe`: `c` cash, `b` bank, `e` energy, `h` happiness, `l` health, `n` knowledge, `p` prices %, `w` pay %, `r` interest points, `j` workplace closure days, `k` clothes wear. A range is written `a~b`. Always go through `applyFx`, which also nudges market mood `S.mkt` when rates, prices or closures change. Writing to `S` directly means the displayed "fx" line will not match the real change. Event sources: `NEWS`, `CHOICES`, `TWISTS`, `STORIES`, `SAGAS` (global storylines, one a game), `INDUSTRY` (industry-specific storylines, one a game, see below), `MACRO` (multi-day shocks) and `basicEvent`/`itemEvent`.

**Macro economy.** News, `MACRO` and `SAGAS` push entries onto `S.trends`; `trendTick` applies each trend's daily `p/w/r/mkt/lay/cls/ill` every night. All of it is scaled by `CONFIG.macro` (`strength` times per-key multipliers via `scaleTrend`/`mk`). The savings rate `S.rate` and market mood `S.mkt` feed `expRet()`, which sets the expected daily return of the fixed deposit (follows `S.rate`) and ETF, hedge fund and crypto (follow `S.mkt`, minus an interest-above-normal term, `CONFIG.market.rateBeta`). When no trend is moving interest, `S.rate` drifts back to `CONFIG.market.rateBase`. **Loan rates (`CONFIG.loan`) are intentionally fixed and must never be touched by macro code.**

**Industry-specific storylines.** Besides the global storyline (`SAGAS`), each game has one industry-specific storyline (`INDUSTRY`, tuned by `CONFIG.industry`) that hits particular workplaces and roles. It may run at the same time as the global storyline; macro shocks keep `CONFIG.events.storylineGap` clear days from both. While it runs, `indRole(c, i)` gives a role's pay multiplier, hiring freeze or opening and cuts; `rolePay(c, i)` is the role's base pay with that change, and every place that shows or pays a shift's pay goes through it (shift length and the work-experience threshold stay on base pay). `rollOpenings` applies the freezes and openings, `indTick` the layoffs and suspensions, and the Employment Office shows a rumour before it starts and an outlook while it runs (`indOutlook`).

**Game modes and AI rivals.** A game is a single game (`S.mode` `'single'`, `CONFIG.time.gameDays` days) or a game with AI rivals (`'rivals'`, `CONFIG.rivals.gameDays` days), chosen on the welcome screen. Always read the game length through `gameLen()` / `maxDays()`, never `CONFIG.time.gameDays` directly: storyline windows, rank target days (`tierDue`, stretched by length) and the time limit all follow it. Rivals are records in `S.rivals`; `rivalTick()` (in `rollover` right after `indTick`) plays each rival's day with the game's own numbers (`rolePay`, `G()`, `qualFee`, `lessonCost`, `indRole`, the endings) and rolls its own dice with `rrand()` from `S.rivalSeed`, never `Math.random`, so single games stay exactly as they were. Rival news goes into the morning notes. A rival game is won on the Life Score (`CONFIG.rivals.scoring`, `LIFE_CATS`, `lifeScore()`): places in each category × weights, from each player's record (`S.life` filled by `lifeSample()` in `rollover`, and each rival's `life`, `rankDay`, `bestJob`). `rivalBoard()` draws the Overview leaderboard and `finish()` shows `lifeTable()` instead of the single-game score. A rival game has `CONFIG.rivals.industryStorylines` industry-specific storylines (`S.indLeft` counts the ones still to come). The job race (`CONFIG.rivals.jobRace`): a role a medium or expert rival just took may be closed for you the next day (`S.raced`, set in `rivalTick`, cleared each morning; `apply()` says who got there first). Relationships (`CONFIG.rivals.social`, each rival's `rel`): `relGain()` applies a change with tension (a gain below 0 may backfire; a backfire, or a call that lands on −1, is an argument and `argue()` takes `social.argument` happiness, so rows that can end in one carry the `chance` class and the UI check compares only their time chip), `maybeEncounter()` (in `enter()`) and `encounterCard()` (top of the building screen, `meet` action), `rivalCall()` (`rcall`: from home or the 📞 Calls app), `congratulate()` (buttons on rival news in the morning pop-up, which shows its results as forced toasts). Building a relationship always costs time. Money between you and rivals (`CONFIG.rivals.money`, the 💬 Messages app `msgsapp`): `S.msgs` (rivals' requests to borrow and bet offers, made by `rivalMsgTick()`), `S.rloans` (`dir` 'in' = a rival owes you, 'out' = you owe a rival) and `S.bets`, settled each morning by `settleMoney()` (both run at the end of `rivalTick`, on the rival dice); `replyMsg()` (`msg`), `askBorrow()` (`rborrow`), `offerBet()` (`rbet`). What they hold counts in `worth()` and `rivalWorth()` through `rivalMoney()`, so money only moves between wallets. settleMoney() snapshots every bet’s growth before issuing any bet payouts or refunds, so simultaneous settlements cannot affect one another. Not paying a rival back in full on the due morning costs `loan.defaultRel` with them, `defaultOthersRel` with every other rival and `defaultHappiness`, once. Living and studying together (`CONFIG.rivals.together`): a flatmate (`S.flat`; `flatmate()`, `myRent(day)` gives your half for the specified bill day and the whole when they skipped that bill; omitted day means the upcoming rent day, `flatShare()` in `rivalNight` takes theirs, `flatTick()` at the end of `rivalTick` does the night together and moving out, `flatRows()`/`flatDo()` the home card, actions `flat`, `unflat`, `fdo`); study groups (`studyPartners()`, `studyGroup()` in `study()`, `groupHap()`/`groupChip()` on the lesson row); rival cards at night (`RIVAL_CARDS`, dealt by `rivalCard()` at the end of `pickNight`, rival dice; `decide()` runs them like any decision and `rivalCardDone()` adds the relationship part and any argument to the card's fx line).

**Careers and study.** `CAREERS` (ladders per workplace, each rank has pay and `need` qualifications) and `TRACKS` (School pathways: Certificate, Degree, Honours, Masters, each made of modules and lessons) are separate tables linked by qualification name. Job knowledge requirements come from `CONFIG.jobs.knowledgeByLevel`. Shift length and energy cost are derived from shift pay through `CONFIG.time.shifts`, so a higher-paying job always works shorter shifts. Check pay-per-hour ordering after editing pay. Actual shift pay (`shiftPay`/`payInfo`) includes knowledge and penalties, while the job board shows base pay.

**Net worth and endings.** `worth()` is the score basis: cash, bank, investments and resale value of belongings, minus hospital debt, rent arrears and any loan. Endings are checked in `stressTick`, `loanTick` and `checkWin`: bankrupt (net worth under a threshold for N consecutive days, counted from `fromDay`), loan default, hospital, exhaustion, morale, time limit.

**Rendering.** `render()` repaints the screen from `S` by calling named parts in order (`renderStats`, `renderPopups`, `renderHud`, `renderOverviewCards`, `renderMap`, `renderWindows`, `renderPanel`, `renderA11y`); there is no framework or virtual DOM. Panel HTML is built in the `panels` map as strings. Buttons are `data-act`/`data-arg` elements; a click on `#shop` runs the matching entry in the `ACTIONS` table, which also says which actions the preview may try and their day-bar colour. Add a feature by adding its panel markup, one `ACTIONS` line and the function it calls. The top-bar "End day" button reads "Sleep outside" when the player is not at home.

**Saves.** `load()` reads the save, `migrateSave()` runs the ordered `MIGRATIONS` steps (blank() defaults, removed jobs and qualifications, old field shapes) and `hydrate()` puts it into play; a save that cannot be loaded is kept as `dailyGrind.save.v1.broken`. When renaming or removing a career line, qualification or `S` field, add a migration step and keep old saves loadable (raise `SAVE_VERSION` for a version-specific change).

## Conventions specific to this repo

- Log every gameplay change in `CHANGELOG.md`, in the existing numbered-section style, including new `CONFIG` keys and removed ones.
- Use a real minus sign (`−`) in player-facing text via the `sg()` helper (`+5` / `−3`); money goes through `money()`.
- Scaling to difficulty, prices and wages goes through `G()` (price index) and `Df()` (difficulty), so use them for any new cost.
- Sleeping at home restores `CONFIG.sleep.perHour` energy (by home) and `CONFIG.health.sleep` health for each hour left in the day, both capped, plus happiness. Sleeping elsewhere earns `CONFIG.sleep.awayShare` of each. Going to bed unfed adds `CONFIG.health.nightly.skippedMeal`. Health otherwise changes only through the `l` token, the gym, the Park, the hospital, meals, hours of work and study (`workHealthPerHour`, `lessonHealthPerHour`, `selfStudy.healthPerHour`) and the nightly rules in `CONFIG.health.nightly`.

## Rival personalities and remembered favours

CONFIG.rivals.personalities and CONFIG.rivals.memory tune the feature. Each rival stores personality plus favours {trust, owed, entries}; SAVE_VERSION 5 migrates old records with prepareRival using a stable rivalSeed/index fallback, without rolling dice. makeRivals assigns distinct personalities using only rrand. Personality changes lending, repayment, betting, friend tips, tension and job-race chances independently of difficulty. All probability offsets and memory bounds are in CONFIG.

remember records meaningful loan help/refusal, expiry, on-time repayment/default and five personal help cards (car, cake, cover, soup, move); chats/calls do not mint favour credits. Refusals weigh more for vindictive rivals. History and trust are capped. favourTick runs after flatTick in rivalTick; on a later morning, one remembered favour can become a job introduction if no tip is active and relationship is at least neutral. It consumes a credit, preserves active tips, and explains the return in morning news. Profiles show personality and recent deeds; the Messages app and encounters use personality-specific context. Keep single-player games free of memory effects and new random draws. Targeted checks are in tools/qa/check-personalities.js; the standard UI fixture includes memories and personalities.
